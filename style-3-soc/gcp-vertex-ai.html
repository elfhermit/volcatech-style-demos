CI-06 · AI · VERTEX AI

Vertex AI

Google Cloud · Machine learning platform

One platform for the whole model lifecycle, from training through deployment to monitoring. Agent building and generative work sit alongside classical machine learning, under the same access controls.

05European regions The Vertex AI locations list includes eleven European regions.

Contact us All ai services

The problem

What teams run into without it.

Notebook-to-production gap

Models that behave well in a notebook stall on the way to production, because serving, scaling and rollback must be engineered separately for every project.

Fragmented ML tooling

Data preparation, training, evaluation, deployment and monitoring live in separate tools, so handovers lose context and nobody owns the model lifecycle end to end.

Model governance blind spots

Without a shared registry and audit trail it is hard to state which model version is live, what data trained it, and whether it still behaves as approved.

Why teams choose it

What Vertex AI is good at.

The whole model lifecycle

Data preparation, training, tuning, deployment and monitoring run under one set of tools. A model does not change hands between systems as it moves from experiment to production.

Google models included

Gemini and the other Google models are available from the same console as your own. Generative work does not need a separate vendor relationship or a second billing account.

Enterprise data boundaries

Training data and prompts are handled under the project's own access controls, not pooled into a shared service. That matters when the material is regulated or commercially sensitive.

Key features

What you get, specifically.

01

Prompt management

Prompts are versioned and compared as artefacts of the project rather than pasted into application code.

02

Vector search

Embeddings are indexed and queried by similarity, which is what retrieval over your own documents needs.

03

Grounding sources

Model answers can be tied to your own corpus, so a response cites material the organisation actually holds.

04

Availability commitment

Google's service level agreement for Vertex AI sets a monthly uptime objective of at least 99.9% for training, deployment and batch prediction, and at least 99.5% for custom-model online prediction served from two or more nodes.

06

Model registry and versions

Trained models are registered as numbered versions with aliases pointing at them, so the team can say which version is serving today and move back to an earlier one without rebuilding it.

07

Skew and drift monitoring

A deployed tabular model is watched on two axes: whether production input still resembles the training data, and whether it has moved away from what production itself looked like earlier. Either comparison can raise an alert on the features you nominate.

Where it fits

Three situations it is built for.

Internal agents

Assistants built against the organisation's own systems and documents, rather than a general model answering from the open web.

Model fine-tuning

Adapting a base model to a domain's own vocabulary and task shape, where prompting alone stops being enough. Supervised tuning, reinforcement learning and preference tuning are each offered for Gemini models, with the methods listed per model, so the approach can follow the task and the labelled material actually at hand.

AutoML builds

A first working model produced from labelled data without a team writing the training loop by hand.

Choosing well

When Vertex AI is the right call — and when it is not.

  • You train, tune or serve your own models on managed infrastructure

    →Vertex AI

  • You mainly consume existing foundation models through an API

    →Model Garden

  • Your questions are analytical and your data already sits in a warehouse

    →BigQuery

  • Serving a self-contained inference container without platform MLOps

    →Cloud Run

Common questions

What evaluators ask.

01How does Vertex AI relate to Model Garden?

Model Garden is the model catalogue inside Vertex AI. You deploy existing models from the catalogue; the wider platform covers training, tuning, serving and monitoring — including models you build yourself.

02Can we keep workloads in European regions?

Yes — the Vertex AI locations list includes eleven European regions, and resources are created in the region you choose. Residency scope still varies by feature and model, so we confirm it per workload during design.

03Will our prompts or tuning data train Google's models?

No. Google's Vertex AI data-governance documentation commits that customer data — prompts, outputs and tuning datasets — is not used for training or fine-tuning of its models unless you give prior permission or instruction. Controls and auditability follow your existing Google Cloud project settings.

04How is Vertex AI charged?

Consumption-based: training compute, serving nodes and managed features are metered separately, so the total depends on architecture and usage patterns. Contact us for an estimate built on your actual workloads.

05Who runs the platform day to day?

Vertex AI removes most infrastructure work, but models still need an owner for evaluation, retraining and monitoring. That role can sit in-house or with a managed partner. [TODO: Volcatech delivery model and response times]

06How do we know a model still behaves the way it did when it was approved?

Monitoring watches the feature values reaching a deployed tabular model and separates two different failures. Skew is judged against the distribution those features had in the training data, and catches production input that never looked like what the model learned from. Drift is judged against the distribution the same features showed in production earlier, and catches input that has shifted since. Comparisons run on a schedule you set, against thresholds you set per feature, so a degraded model surfaces as an alert rather than as a business result months later.

07Can training be repeatable rather than a notebook someone remembers to run?

Yes. A pipeline describes the steps as code and runs them as a managed workflow, so preparation, training, evaluation and registration happen in the same order every time, with no infrastructure to stand up for a run. Steps whose inputs have not changed can reuse the previous result instead of recomputing it, and each run records the artefacts it produced, so months later it is still possible to say which data and which code produced a given model version.

08Can prediction endpoints be kept off the public internet?

Yes, and it is a design decision rather than a later hardening step. Endpoints can be published privately through Private Service Connect so that calls reach them across your own network instead of a public address, and the service can be placed inside a VPC Service Controls perimeter that limits which projects and networks may reach it at all. Coverage differs by model type — tuned Gemini models, for one, are served from shared public endpoints — so the network design is confirmed per workload. It is best settled before applications are written, because moving an endpoint afterwards means changing every caller.
