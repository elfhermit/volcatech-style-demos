CI-05 / Databases — Google Cloud service

CI-05 · DATABASES · DATASTORE

Datastore

Google Cloud · Datastore-mode database

A document database for back-end services, running on the Firestore engine in Datastore mode. Growth in traffic is absorbed by the service rather than by a sharding scheme you maintain.

04Query scaling model Query cost is designed to track the result set you ask for, not the volume of data stored, so response times stay stable as datasets grow.

Contact us All databases services

The problem

What teams run into without it.

Schema migrations at scale

Rigid relational schemas turn every product iteration into a migration exercise. Altering large tables means locks, downtime windows and deployments that have to be coordinated across teams.

Scaling as a project

Growth in a self-run key-value or document store means capacity planning, sharding and rebalancing — infrastructure work that lands on developers instead of the product.

Integrity in app code

Many horizontally scaling stores give up transactional guarantees, pushing consistency checks into application code where they are duplicated, drift apart and eventually get something wrong.

Why teams choose it

What Datastore is good at.

Documents, not rows

Entities are stored as documents with their own fields. Records whose shape varies do not force a schema migration on the rest.

No sharding to design

Partitioning and rebalancing are handled by the service. Growth in request volume does not turn into a data layout project.

Transactions still hold

Writes across several entities commit or fail together, as they would in a relational engine. Scale is not bought by giving up transactional guarantees.

Key features

What you get, specifically.

01

Multi-region replication

Data is copied across regions, so the loss of one does not take the database with it.

02

Automatic indexing

Single-property indexes are maintained as entities are written; composite indexes are declared where a query needs them.

03

Query engine

Filters, ordering and pagination run against the index rather than scanning the entity set.

05

Availability commitment

Datastore mode runs on Firestore's storage layer and shares its availability and scaling characteristics.

06

Entity size ceiling

A single entity is capped at 1,048,572 bytes — a mebibyte less four bytes — so large files belong in object storage with the entity holding the reference.

07

Indexed string limit

An indexed string property is limited to 1,500 bytes of UTF-8, so longer text is kept unindexed and what is searchable is decided when the model is designed.

Where it fits

Three situations it is built for.

Server-side data

Back-end services whose read volume is high and whose access pattern is known in advance.

User directories

Profile and account records looked up by key, where the record shape differs between user types.

Product catalogues

Item data with attributes that vary by category, read far more often than it is written. Attributes that are only ever displayed, never filtered on, can be kept unindexed, which holds the index set down to the queries that exist.

Choosing well

When Datastore is the right call — and when it is not.

  • New document-database projects

    →Firestore

  • Existing systems built on the Datastore API

    →Datastore

  • Relational queries, joins and SQL reporting

    →Cloud SQL

  • Analytics across stored entities

    →BigQuery

Common questions

What evaluators ask.

01What is the relationship between Datastore and Firestore?

Firestore is the next generation of Datastore. The service now runs as Firestore in Datastore mode, on Firestore's storage layer, so it inherits the same availability and scaling while keeping the original Datastore API.

02Should a new project start on Datastore?

Usually not. Google steers all new builds towards Firestore in Native mode. Datastore mode remains the right choice where existing code depends on the Datastore API or a server-side entity model.

03Does Datastore support transactions?

Yes — atomic transactions with strong consistency across queries, which is unusual among horizontally scaling NoSQL stores. Integrity rules can stay in the database rather than migrating into application code.

04Can we change modes later?

Only an empty database can switch between Native and Datastore modes, so the decision should be made deliberately at project start rather than deferred.

05Where does the data live?

Each database is provisioned in a location you choose, including EU regions, and entity data is stored there. Settle residency constraints before creation — the location of an existing database cannot be changed.

06Do the original Datastore limits still apply?

Several of them no longer do. Now that the service runs on the Firestore storage layer, the old ceiling of one write per second to an entity group has gone, transactions are no longer confined to a fixed number of entity groups, and strong consistency no longer depends on writing ancestor queries. Designs carried over from the original Datastore are usually holding constraints that were lifted underneath them.

07Which query patterns does Datastore mode not cover?

There are no joins, and no filtering on the result of a subquery; every query is answered from an index that already exists when it runs. Access patterns therefore have to be settled while the model is being designed rather than discovered later, and reporting that depends on relational queries is better answered from a system built for it.

08How do we get entities out for backup or analysis?

A managed export writes entities to a Cloud Storage bucket and can be put on a schedule; an export that names the kinds it covers can then be loaded into BigQuery. One caveat belongs in the plan: the export reads eventually rather than freezing the database, so an entity written while the job is running may or may not appear. Anything that needs a single consistent instant has to come from elsewhere.
