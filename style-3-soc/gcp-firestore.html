CI-05 / Databases — Google Cloud service

CI-05 · DATABASES · FIRESTORE

Firestore

Google Cloud · Document database

A document database that talks to the client directly. Changes are pushed to connected devices as they happen, and the local cache keeps the application usable while the connection is gone.

Contact us All databases services

The problem

What teams run into without it.

Hand-built sync layers

Keeping mobile, web and backend state consistent means writing and operating polling, push and conflict-resolution code — a synchronisation layer the product team then maintains for the life of the app.

Offline as an afterthought

Field and consumer apps stop working the moment connectivity drops, unless local caching and re-sync are engineered in — work that rarely survives the first release plan.

Capacity planning at launch

Provisioning a database before real traffic exists forces a guess. Under-size it and launch suffers; over-size it and the organisation pays for idle capacity from day one.

Why teams choose it

What Firestore is good at.

Changes pushed to clients

The database sends updates to subscribed devices instead of waiting to be polled. Screens showing the same record stay in step without a message layer in between.

Works while offline

Reads and writes go to a local cache when the network drops, and reconcile when it returns. The application does not need a separate offline path.

Rules enforced at the database

Access is expressed as rules on documents and fields, evaluated by the service. A client can talk to the database directly without that becoming an open door.

Key features

What you get, specifically.

01

Client SDKs

Native libraries for iOS, Android and the web connect to the database without a back- end service in between.

02

Security rules

Read and write permissions are declared per collection, document and field, and evaluated on every request.

03

Multi-region transactions

Transactions commit or roll back across replicas in more than one region, without a queue to reconcile afterwards.

04

Availability commitment

Multi-region Firestore carries a 99.999% monthly uptime SLA; regional deployments carry 99.99% in most Google Cloud regions.

05

Indexing default

Queries are indexed by default, and performance tracks the size of the result set rather than the dataset.

06

Document size ceiling

A document holds up to 1 MiB (1,048,576 bytes) and collections nest up to a hundred levels deep — both are modelling limits rather than quotas to be raised.

07

Recovery window

With point-in-time recovery enabled, one version of each document is kept per minute for seven days, and the last hour can be read at finer granularity.

Where it fits

Three situations it is built for.

Mobile applications

Client applications that read and write directly, with the network treated as intermittent by default.

Collaboration tools

Chat and shared editing, where two people looking at the same document should see the same thing.

Game state

Session and player state shared between devices in a match, updated as the state changes. Session records that should not outlive the match can carry an expiry field, and the service removes them without a clean-up job to run.

Choosing well

When Firestore is the right call — and when it is not.

  • New document-database builds, especially with mobile or web clients

    →Firestore

  • Server-side systems already on the Datastore API

    →Datastore

  • Relational transactions and SQL reporting

    →Cloud SQL

  • Event analytics at warehouse scale

    →BigQuery

Common questions

What evaluators ask.

01How does Firestore relate to Datastore?

Firestore is the successor — the current generation of Google's document database. A separate Datastore mode preserves the older API for existing systems, while Native mode, the recommended choice for new builds, adds real-time sync and offline support.

02Does Firestore work offline?

Yes. Client SDKs keep a local copy of active data, so apps read, write and query while disconnected and reconcile changes automatically once the device is back online.

03Can we meet EU data residency requirements?

Firestore databases are created in a specific location, which can be an EU region; document data is stored there. Multi-region configurations replicate within the selected geography, not across it.

04How reliable is Firestore in production?

Google commits to 99.999% monthly uptime for multi-region deployments and 99.99% for regional ones in most regions. Replication and scaling are handled by the service rather than by your team.

05What drives Firestore costs?

Charges follow document reads, writes, deletes, storage and network egress, so cost tracks how the application actually behaves. Model your access patterns first — contact us and we will analyse them with you.

06Do we need our own push or websocket layer?

No. A listener receives a snapshot of the data when it attaches and then only the changes that follow. Local writes fire the same callbacks straight away, before the server has confirmed them, and each document carries a flag showing whether it still has writes pending — which is what lets an interface feel immediate without pretending the change is durable yet.

07Can we recover from a bad write or a mistaken deletion?

With point-in-time recovery switched on, the database keeps one version of each document per minute for seven days. A targeted fix reads the affected documents as they stood at a chosen minute and writes them back; a wider one clones the database, or exports and imports it, at a past timestamp. Within the last hour, states can be read at finer granularity — read only, not exported.

08How do we stop expired records accumulating?

A time-to-live policy points at a single timestamp field within a collection group, and documents go once that time has passed — typically within a day of it rather than at the instant it is reached. Two behaviours belong in the design: expired documents still appear in queries until the deletion actually runs, and subcollections beneath a deleted document are not removed with it.
