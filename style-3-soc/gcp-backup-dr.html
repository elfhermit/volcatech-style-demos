Backup and DR

Google Cloud · Backup and recovery

One place to define backup policy for virtual machines, databases and file shares. Copies are application-consistent, so a restore returns a system that starts rather than files that need repair.

04Backup immutability Backup vault storage enforces both immutability and indelibility: stored backup data can neither be modified nor deleted during its retention period.

Contact us All storage services

The problem

What teams run into without it.

Backup windows that overrun

Nightly full backups no longer fit the night. Jobs spill into working hours, throttle production systems and force a choice between coverage and performance.

Backups within ransomware's reach

Backups kept on the same network with the same credentials get encrypted alongside production data. A copy of last resort that stays writable is not a copy of last resort.

Untested, scattered recovery

Across the organisation every system has its own backup tool, licence renewal and owner. Nobody has rehearsed a full restore, so recovery time is a guess made during a crisis.

Why teams choose it

What Backup and DR is good at.

One console for the estate

Virtual machines, databases and file systems are covered by the same policies and the same schedule. There is no separate tool per workload type to keep in step.

Recovery you can plan

Recovery point and recovery time objectives are set per policy rather than discovered during an incident. What a restore will cost in time is known in advance.

Copies that restore cleanly

Backups are quiesced at the application layer, not taken as a raw disk snapshot mid- write. A database comes back in a state it can open.

Key features

What you get, specifically.

01

Incremental copies

After the first copy only changed blocks are stored, which keeps repeat backups from re-writing the whole dataset.

02

Database support

Oracle, SQL Server and SAP HANA are handled as applications, not as the disks they happen to sit on.

03

Policy-based schedules

Retention and frequency are attached to a policy, so adding a workload means assigning it rather than configuring it.

05

Schedule granularity

Rules run hourly, daily, weekly, monthly or yearly, each with its own retention and a start window of no less than six hours; one plan cannot hold two rules on the same frequency.

06

Where a vault can sit

A vault is created either in a single region or in one of the multi-regions covering Asia, the EU and the United States. The choice narrows by workload: a vault holding AlloyDB backups has to sit in the region its source cluster sits in, while a Filestore vault can be placed in a second region but not in a multi-region.

Where it fits

Three situations it is built for.

Ransomware recovery

A clean copy held outside the production environment, so recovery does not depend on the compromised systems.

Regulatory retention

Records kept for the period a regulator requires, with the retention set once and applied by policy.

Cross-region DR

A second region holds recoverable copies, so a regional outage has a defined path back to service.

Choosing well

When Backup and DR is the right call — and when it is not.

  • You need policy-driven, immutable protection across VMs, databases and file systems

    →Backup and DR

  • Long-term archives, not application-consistent recovery points

    →Cloud Storage

  • A managed database whose built-in automated backups already meet your needs

    →Cloud SQL

Common questions

What evaluators ask.

01What workloads can it protect?

Compute Engine VMs and disks, VMware Engine VMs, Cloud SQL and AlloyDB, databases you run yourselves — Oracle, SQL Server, SAP HANA — and NFS and SMB file shares, all brought under one managed backup service.

02How does it differ from copying backups into Cloud Storage?

A bucket stores whatever you copy into it; scheduling, application consistency and restore testing remain your job. Backup and DR adds policy-based scheduling, incremental capture, application-consistent recovery points, and a vault whose contents cannot be altered.

03Does it stop ransomware deleting our backups?

Backups in a backup vault are immutable and indelible until their retention expires — they cannot be rewritten or purged. Self-managed snapshot storage does not carry the same guarantee.

04Where do the backup copies live?

Backup vaults are created in the region or multi-region you select, so copies can stay within EU boundaries. Vault storage is Google-managed and sits outside your own projects, separating it from production credentials.

05What drives the cost of backup?

Stored vault capacity, the number of protected workloads and retention length are the main drivers; incremental capture keeps stored volume below repeated full copies. Contact us for an estimate modelled on your estate.

06Can protected copies be used for anything besides recovery?

Where the estate is protected through a backup/recovery appliance, yes. A copy can be cloned into an independent dataset for user acceptance testing, audit work or e-discovery, and a live clone can be refreshed on demand or on a schedule so a test environment tracks production without a fresh full copy each time. Copies written into a backup vault are there to be restored from — the clone and mount options belong to the appliance-managed path, which is worth knowing before a team plans around them.

07Once backups exist, who can shorten how long they are kept?

Nobody, and that is deliberate. The floor is a property of the vault rather than of anyone's permissions: a vault is created with a minimum enforced retention of anywhere from one day to 99 years, and a backup rule writing into it may keep copies for longer but never for less. A backup becomes eligible for deletion only once that period has passed — which is the difference between a retention policy and a retention intention.
