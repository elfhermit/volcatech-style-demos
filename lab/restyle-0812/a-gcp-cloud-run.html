Cloud Run

Google Cloud · Serverless containers

A managed platform for running containers. Bring an image in any language and it scales with the traffic — down to nothing when there is none.

01Scale to zero With no traffic the service holds no instances, and starts again on the next request.

Contact us All serverless services

The problem

What teams run into without it.

Idle capacity costs

Container workloads with uneven traffic still occupy servers around the clock. Teams keep paying for compute that sits unused between peaks, because the platform cannot release it.

Cluster overhead for small services

Running a handful of containerised services should not require a full Kubernetes cluster. Provisioning, patching and upgrading nodes consumes engineering time out of proportion to the workload.

Repeated per-service plumbing

Every new service repeats the same setup: load balancing, certificates, autoscaling rules and deployment pipelines. Each copy is another thing to maintain and another place to make mistakes.

Why teams choose it

What Cloud Run is good at.

Deploy the container, not the platform

If it builds into an image and listens on a port, it runs here. There is no cluster to size, patch or keep alive between deployments.

Billed by request

An idle service costs nothing. Traffic that arrives in bursts is charged as bursts rather than as capacity reserved for the peak.

No language constraints

Runtime, framework and dependency set are decided inside the image. The platform does not have an approved list.

Key features

What you get, specifically.

02

HTTPS endpoint on deploy

Each service gets a TLS endpoint when it is created — no load balancer or certificate step in between.

03

Fast autoscaling

Instance count follows concurrent requests closely enough that traffic spikes do not need to be predicted in advance.

04

Availability commitment

Cloud Run services (non-GPU) carry a 99.95% monthly uptime service level objective in most cloud regions.

05

Scale ceiling

A single service can scale out to as many as one thousand instances under default quota, with higher ceilings available on request.

06

Long-running requests

A single request may run for up to 60 minutes when the timeout is raised; the default cut-off is five minutes.

07

Per-instance concurrency

One instance can serve up to 1,000 concurrent requests, with the ceiling configurable per service revision.

Where it fits

Three situations it is built for.

RESTful APIs

Request-response services whose load is uneven, where paying for idle capacity overnight is the main waste.

Web application back ends

The server-side half of an application, deployed from the same image the team already builds in CI.

Internal automation

Webhook receivers, scheduled jobs and bot services that run rarely and should not carry a permanent host. Work that must run to completion rather than serve requests fits Cloud Run jobs, triggered on demand or on a schedule.

Choosing well

When Cloud Run is the right call — and when it is not.

  • Stateless HTTP services or event-driven containers with spiky traffic

    →Cloud Run

  • You need full cluster control: custom operators, node tuning, service mesh

    →Kubernetes Engine

  • Long-lived stateful workloads or licensed software tied to a VM

    →Compute Engine

  • An existing App Engine estate that works and needs no migration

    →App Engine

Common questions

What evaluators ask.

01Cloud Run or App Engine — which should we choose for a new build?

For new workloads, Google's own documentation points to Cloud Run as the current serverless direction. App Engine remains fully supported, so existing estates need not move. We assess this per application rather than by default.

02Do we need Kubernetes skills to run it?

No. Cloud Run accepts a container image and handles scheduling, scaling and TLS itself. Many organisations adopt it with no Kubernetes expertise in-house; Kubernetes Engine is for when you want cluster-level control, not a prerequisite.

03What happens when traffic drops to zero?

Services scale down to no running instances by default, then scale back out when requests arrive. If cold starts matter on latency-sensitive paths, a minimum instance count can be configured.

04Are we locked into specific languages?

No. Anything that can be containerised and serve HTTP will run, whatever the language or framework. For common runtimes, source-based deployment can build the container for you.

05How is Cloud Run priced?

Billing follows actual usage — CPU, memory and request volume — so cost depends on traffic shape and configuration. Contact us and we will model it against your expected workload.

06Can we release gradually and roll back quickly?

Yes. Each deployment creates a new revision, and traffic is split between revisions by percentage — a new version can take a small share first, then more as monitoring stays clean. Rolling back means pointing traffic at the previous revision again.

07Is Cloud Run only for request-and-response services?

No. Cloud Run jobs run a container to completion for batch-style work, on demand or scheduled, and worker pools handle always-on consumers that pull from queues or message brokers. Services, jobs and worker pools share the same image format and operating model.

08Do WebSockets, gRPC or streaming responses work?

Yes. Connections are served over TLS that the platform manages, with HTTP/2 and gRPC supported end to end and WebSockets available for long-lived connections — subject to the configured request timeout.
